# Vouchcode: Comprehension Verification as a Second Condition for Accountable AI-Assisted Software Development

**Author:** Sudais Khalid ([sudaiskhalid.com](https://sudaiskhalid.com))

**Repository:** https://github.com/sudais-khalid/VOUCHCODE

**Version:** 0.1.0, evaluated at 62 commits

---

## Abstract

Tooling for tracking AI authorship in source code has converged on a single question:
which lines were generated by a machine. This paper argues that authorship attribution,
however accurate, is insufficient for accountability, because it establishes the origin of
text without establishing whether the human who committed that text understands it. A
developer may accept a generated function without reading it, commit it under their own
name, and satisfy every attribution mechanism currently available.

We present Vouchcode, a local-first system that adds a second condition. Where code is
attributed to AI generation, the committing developer is required to answer questions
derived deterministically from that code's own control flow before the commit is sealed
into a hash-chained, Ed25519-signed ledger. Question generation and answer scoring use
only the Python standard library's abstract syntax tree module and rule-based extraction,
with no language model in the runtime path, which makes results reproducible by the party
receiving a report rather than dependent on the party producing it.

We describe the system's five layers, the deterministic scoring method and its
discrimination between correct, superficial, and confidently incorrect answers, and the
tamper-evidence construction. We report self-application to the system's own repository:
812 hunks across 62 commits, 45.2 percent of changed logic attributed to AI generation
at a mean stylometric confidence of 0.245 against a hard cap of 0.75. We argue that this
number is a conservative underestimate and explain why. We describe the development
methodology used, in which each phase was accepted only after an adversarial exit
criterion was shown to fail correctly against a deliberately broken implementation, and we
report the defects that methodology surfaced. Finally we state the system's limitations
without qualification, including the classes of adversary it does not defeat.

**Keywords:** software provenance, AI-assisted development, code comprehension,
abstract syntax tree analysis, tamper-evident logging, Ed25519, developer accountability,
academic integrity

## 1. Introduction

### 1.1 Motivation

A substantial and growing share of code entering production repositories is not typed by
the developer who commits it. Git, the dominant version control system, was designed on
the assumption that a commit's named author is also its intellectual originator. The
metadata it captures, an author name, an email address, and a timestamp, cannot
distinguish a line a person wrote from a line they accepted from a suggestion.

This gap appears in three settings that motivate the present work. In academic assessment,
an examiner cannot determine whether a submission reflects the student's understanding or
an unexamined machine output. In technical hiring, an employer faces the same uncertainty
evaluating a take-home submission or a portfolio. In software supply chains, compliance
processes increasingly require verifiable provenance for material code changes.

### 1.2 Problem statement

Existing tooling addresses the question of what generated a segment of code. It does not
address whether the accountable human party understands that code well enough to be
responsible for it. Attribution checks verify authorship of text; they do not verify
comprehension of logic. A developer who never reads a generated function passes every such
check.

We take the position that **authorship attribution is a necessary but insufficient
condition for accountable AI-assisted development, and that verifiable comprehension is
the missing second condition.**

### 1.3 Contributions

1. A comprehension verification method that derives questions from a code fragment's own
   control flow and scores natural-language answers against facts extracted from its
   abstract syntax tree, with no external model and therefore reproducible output.
2. A scoring construction that separates three answer classes which term-overlap methods
   conflate: correct, superficially keyword-matched, and fluent but incorrect.
3. An attribution model that distinguishes proof, evidence, and inference as separate
   epistemic categories carried through to the report, rather than presenting them as one
   confidence number.
4. A function-level segmentation method that distinguishes a rename from a rewrite, so
   previously understood code is not re-presented for verification.
5. A tamper-evident ledger whose verification reports per entry and identifies the first
   point of failure, with a distinct outcome category for fingerprints that are
   cryptographically sound but computed under non-comparable conditions.
6. A development methodology in which each phase defines an adversarial exit criterion in
   advance and is accepted only once the implementation is shown to fail correctly when
   deliberately broken. We report the defects this surfaced.

### 1.4 Scope

The implementation targets Python source, using the standard library `ast` module.
Extension to other languages through tree-sitter is future work and not claimed here. The
system is designed for individual developers and small teams in local development
environments.

## 2. Related work

We describe the landscape in general terms. We deliberately cite no external measurements
or publications, because we have not independently verified any, and a paper arguing for
honest reporting should not import numbers it cannot check.

**Enterprise provenance platforms** capture AI tool usage on the client and write
structured metadata into git-native mechanisms so that attribution survives merges and
rebases, presenting results through a hosted dashboard. Their deployment model generally
requires organizational authorization into a vendor platform, so provenance metadata leaves
the developer's machine.

**Endpoint traceability tools** observe assistant activity at the operating system or
editor level and track generated code through continuous integration into deployment.
These are typically deployed through device management infrastructure, placing them outside
the reach of an individual developer.

**Open-source git-native tools** hook into assistants at generation time, fingerprint the
output, and preserve that metadata through git operations, enabling a line-level blame that
distinguishes AI from human authorship. These address the deployment and data residency
concerns of the enterprise category while remaining limited to attribution.

**Disclosure conventions** have converged across open-source projects on declaring AI
assistance in commit messages through a dedicated trailer, distinct from human
co-authorship trailers, on the principle that accountability, unlike assistance, cannot be
held by a model. Vouchcode adopts that principle and extends it by requiring accountability
to be demonstrated rather than asserted.

**Supply chain attestation frameworks** provide cryptographic attestation of build
provenance, binding signing keys to verified identities. These currently lack a native
field for AI authorship and operate at release rather than commit granularity. Vouchcode's
ledger is designed in the spirit of this model, applying comparable rigor at the commit
level while remaining self-hosted.

**Research gap.** Across these categories, every mechanism terminates at the question of
origin. None extends to the question of understanding. That is the gap addressed here.

## 3. System architecture

Vouchcode is structured as five cooperating layers, implemented across 40 Python modules.

### 3.1 Design principles

- **Local-first.** All analysis, signing, and storage occur on the developer's machine.
  No source code and no provenance data is transmitted anywhere.
- **Verify before trust.** AI-generated code is not treated as accepted until the
  responsible developer demonstrates structural understanding of it.
- **Zero external model dependency.** Questions are derived deterministically from the
  syntax tree, not generated by an external model. This preserves privacy and, more
  importantly for evaluation, reproducibility: the same answer receives the same score on
  any machine, offline, at any time.
- **Minimal deployment friction.** Installation and initialization reduce to a single
  command with no account creation.
- **Portability of proof.** Output is a self-contained artifact a third party can check
  without installing the tool.

### 3.2 Layer 1: Capture

Three git hooks are installed at initialization. `pre-commit` records the staged change set
while the index still describes it and is the point at which a commit can still be refused.
`post-commit` resolves the commit hash, which exists only after the commit is written.
Neither hook alone observes both facts.

`post-merge` exists because git does not run the commit hooks for a merge commit it creates
itself. Without it, `git merge --no-ff` leaves a commit in history with no ledger entry.
This defect was found by empirical testing rather than by reading documentation, and is
reported in Section 6.2.

Where an assistant reports which lines it generated, that signal is authoritative. The
system defines a signal file format that any integration may write, and ships an adapter
registering as a Claude Code `PostToolUse` hook. Reading a locally written file is not a
network call and does not violate the zero-model constraint.

Absent a direct signal, a stylometric fallback compares statistical characteristics of new
code against a baseline from the developer's prior work in the repository. Section 7.1
reports what this is and is not worth.

### 3.3 Layer 2: Segmentation

Rather than operating on line diffs, which misattribute formatting changes and fragment
one logical edit across ranges, each changed file's pre- and post-commit versions are
parsed into abstract syntax trees and compared structurally.

The method is deliberately not a general tree edit distance algorithm. Such algorithms are
expensive and, more consequentially, easy to get subtly wrong in ways that pass a small
test suite and then misattribute real code. Instead:

1. Every definition is extracted with a qualified name. Class bodies are descended into so
   methods are independent units; function bodies are not, so a closure remains part of its
   enclosing function.
2. Two fingerprints are computed per definition. The **exact** fingerprint is an `ast.dump`
   with the definition's own name blanked, so a rename does not disturb it. The
   **normalized** fingerprint additionally alpha-renames locally bound names, so renaming a
   variable inside the body does not disturb it either.
3. Definitions are matched by qualified name first. Remainders are paired across the
   removed and added sets by fingerprint equality, then by structural similarity.

Alpha-renaming covers only names a definition binds: parameters, assignment targets, loop
and comprehension targets, `with` and `except` aliases, walrus targets, and nested
definition names. Attribute names, called globals, and constant values are never
normalized, because calling a different method or returning a different constant is a real
behavioral change.

This yields six outcomes: `added`, `removed`, `modified`, `renamed`, `renamed_modified`,
and `moved`. Only `added`, `modified`, and `renamed_modified` carry new logic. A pure
rename or move is attributed `unchanged` with source `structural` at confidence 1.0 and is
never sent through comprehension verification.

### 3.4 Layer 3: Comprehension

For each hunk attributed to AI generation, the engine extracts checkable structural facts.
A fact carries three separable fields: a **subject**, a **condition**, and an **outcome**.
The separation is what makes scoring able to distinguish an answer that names the right
terms from one that relates them.

Facts are drawn from guard clauses that terminate control flow, iteration over collections,
loop termination conditions, and exception handlers. Questions are templated over the facts
of the specific hunk, so the question set differs with the code rather than being drawn
from a fixed bank.

Scoring is described in Section 4.

### 3.5 Layer 4: Ledger

Each entry incorporates the SHA-256 hash of its predecessor's canonical serialization and
is signed with a locally generated Ed25519 key. The genesis entry carries a defined
constant of sixty-four zeros rather than a null, so that every `previous_hash` field has
the same shape and a verifier compares a value rather than special-casing an absence.

Canonical serialization sorts keys, uses tight separators, escapes non-ASCII, and excludes
the entry's own hash and signature by explicit name rather than by inference. Sorted keys
mean a ledger reformatted by a different serializer still verifies.

Critically, chain links compare against the predecessor's **recomputed** hash, not its
stored one. This is what makes tampering propagate: an edited entry retains its old stored
hash, so comparing against that value would confine the damage report to a single entry and
leave every following entry appearing intact. Section 6.2 reports that this was originally
implemented incorrectly and was caught by the phase exit criterion.

### 3.6 Layer 5: Reporting

On request the ledger, or a commit range, is compiled into a signed JSON document and a
human-readable PDF. Both embed the public key and display its fingerprint in a grouped,
uppercase form intended for comparison by eye or by voice.

Both formats render one shared summary module, so they cannot report different numbers for
the same range.

## 4. Methodology

### 4.1 Deterministic answer scoring

The central methodological problem is that term matching is trivially defeated. An answer
that returns every word from the code hits every term a correct answer would hit. A scorer
counting term overlap cannot distinguish them, and would produce a signed attestation that
a developer understood code they never read. That failure would be worse than having no
comprehension layer.

Three answers to the same question must therefore land in three places:

| Class | Description |
| --- | --- |
| Correct | Relates the condition to the outcome and names the outcome the code produces. |
| Superficial | Contains the right terms without connecting them into a claim. |
| Incorrect | Fluent and connected, but asserts an outcome the code does not produce. |

Separation without a language model rests on three measurements:

**Relevance.** Does the answer refer to this fact at all, by naming the subject or the
condition.

**Outcome family.** Does it assert the outcome the code actually produces, judged by
family rather than word overlap, so that "returns None" and "raises an error" are
recognized as different claims. Asserting two mutually exclusive terminal families is
hedging and does not pass.

**Coherence.** Is the answer written as prose rather than assembled as a word list.
Measured as a composite of function word density, the presence of a word that links a
condition to a consequence, and the proportion of content words that are the answer's own
rather than echoed from the code. A regurgitation is composed entirely of echo.

The stuffing gate applies only where stuffing is possible, that is, where an answer names
several distinct terms while lacking the grammar to connect them. A terse correct answer of
two words has no function words either, and penalizing it would punish precision.

### 4.2 Attribution as three epistemic categories

The system does not report one confidence number. It reports which mechanism produced a
classification, because the three are not interchangeable:

| Source | Confidence | Epistemic status |
| --- | --- | --- |
| `structural` | 1.0 | The syntax tree proves the logic did not change. Certainty. |
| `tool_signal` | 1.0 | An assistant reported which lines it generated. Evidence. |
| `stylometry` | capped below 0.75 | The code diverges from prior style. Inference. |

The stylometric path declines to classify at all when the baseline is under twelve prior
definitions or the hunk under twenty syntax nodes, returning an explicit unclassified
result with a stated reason rather than a low-confidence guess.

### 4.3 Fingerprint version tagging

`ast.dump` output is not stable across Python versions. A ledger written under one
interpreter and verified under another would show fingerprints that do not match, and a
verifier would have no way to distinguish an interpreter difference from tampering.

Rather than attempt a version-independent serialization, which is a substantially larger
commitment than the problem warrants, each entry records the conditions under which its
fingerprints were computed: the algorithm version, the interpreter's major and minor
version, and a hash of how that interpreter serializes a probe module exercising every
construct the fingerprinter relies on. The probe is the load-bearing component; the version
number alone would be a proxy.

Verification treats non-comparable conditions as their own outcome category, distinct from
both verified and tampered, and exits zero, because the ledger is sound and only the
fingerprint comparison is unavailable.

### 4.4 Adversarial phase methodology

This is the aspect of the work we consider most transferable, and it is documented in the
commit history rather than reconstructed after the fact.

Development proceeded in six phases. Before implementation of each phase, an **adversarial
exit criterion** was fixed in advance: a specific hard case, chosen as the one most likely
to be silently wrong, that the implementation had to handle correctly. A phase was accepted
only when that case was demonstrated, and in several phases only after the implementation
was **deliberately broken** to confirm the test detected the breakage.

| Phase | Adversarial exit criterion |
| --- | --- |
| 1 Foundation | A commit produces a matching ledger entry, asserted on recorded content rather than on exit status. |
| 2 Segmentation | A function renamed **and** given an internal variable rename is distinguished from both a rewrite and no change. |
| 3 Comprehension | Three answers to one question, correct, keyword-stuffed, and confidently wrong, score differently and in the right order. |
| 4 Ledger | Three chains over the same content produce three outcomes: verified, tampered with the first failure named, and non-comparable. |
| 5 Reporting | Three reports produce three outcomes, including a forged report that verifies internally and is caught only by fingerprint comparison. |
| 6 Evaluation | Self-application to the system's own repository. |

The mutation step is what distinguishes this from ordinary test-driven development. In
Phase 2, disabling alpha-renaming and the similarity fallback produced exactly the failure
the criterion named: `expected one change, got ['added', 'removed']`. Under the same
sabotage, **the pure-rename test still passed.** Had only the easy case been written, a
completely broken tree-diff would have shown green. This is reported because it is
evidence that the harder criterion was doing the work.

## 5. Evaluation

### 5.1 Method

Two forms of evaluation are reported: a test suite whose cases encode the adversarial exit
criteria above, and self-application of the system to its own repository.

We do not report an attribution accuracy figure against labelled ground truth. Constructing
such a corpus would require repositories with reliable per-hunk labels of AI involvement,
which we do not have and did not construct. Reporting an accuracy number derived from data
we generated ourselves would be circular, and we decline to do it.

### 5.2 Test suite

147 tests. Tests drive real git repositories in temporary directories rather than mocking
git, because each exit criterion is a claim about behavior when git actually executes a
hook, and a mocked git cannot substantiate that claim.

Continuous integration runs the suite, a linter, a formatter check, and a type checker
across Python 3.10 through 3.13 on Linux and 3.12 on Windows. Windows is included
deliberately: the capture layer writes hook scripts with forced LF line endings and an
absolute interpreter path because git for Windows executes hooks through `sh`, and that
path requires a real runner to remain honest.

### 5.3 Self-application

The system was applied to its own repository. History predating adoption was reconstructed
by retroactive scan; commits after adoption were captured live.

| Measure | Value |
| --- | --- |
| Commits in ledger | 62 |
| Reconstructed by retroactive scan | 50 |
| Captured live | 12 |
| Hunks analyzed | 812 |
| Hunks carrying new logic | 646 |
| Hunks proven unchanged | 166 |
| Lines of changed logic | 17,324 |
| AI-attributed | 45.2 percent (7,825 lines) |
| Human-attributed | 51.4 percent (8,899 lines) |
| Unclassified | 3.5 percent (600 lines) |
| Chain verification | 62 entries verified, chain intact |

Attribution by source:

| Source | Hunks |
| --- | --- |
| `structural` | 166 |
| `stylometry` | 646 |
| `tool_signal` | 0 |

Stylometric confidence across 566 scored hunks: minimum 0.10, maximum 0.641, **mean
0.245**, against a hard cap of 0.75.

## 6. Results

### 6.1 Interpretation of the self-application figures

**45.2 percent of changed logic is attributed to AI generation, and this is an
underestimate.** Two properties of the measurement push in that direction and are recorded
here rather than omitted.

First, every attributed hunk came from stylometry. No tool signal survives for a commit
made before the adapter existed, so the retroactive scan had only inference available.

Second, and more consequentially, the scan's stylometric baseline is drawn from the
repository's current head, which **includes the AI-written code being scored against it**.
This biases the measurement toward classifying that code as resembling the developer's own
style. The bias is conservative, so the heuristic under-reports AI content on precisely the
repository where AI content is highest.

The mean confidence of 0.245 is the honest summary: this is weak evidence, and the system
reports it as weak evidence rather than presenting 45.2 percent as a measurement.

The comprehension pass rate is reported as absent, not as zero. Fifty commits are
retroactive and excluded by decision, and the live commits since adoption contained no
AI-attributed Python hunks that reached an interactive verification prompt. A rate of zero would read as universal failure, which
is a materially different and false claim.

### 6.2 Defects surfaced by the adversarial methodology

Each of the following was found by an exit criterion or by empirical testing, and each
would have been plausible to ship.

**Merge commits produced no ledger entry.** Git does not run commit hooks for merges it
creates. Found by empirically testing a `git merge --no-ff` rather than assuming hook
coverage. A silent gap in a provenance ledger is worse than a coarse record.

**The similarity signature was too weak.** The first implementation compared bare AST node
type names. Under it, `value.strip()` and `other.upper()` scored 1.0 similarity and were
paired as a rename, because their node types are identical. Thresholds were subsequently
derived from measurement rather than intuition: single-expression functions all measured
nine tokens and scored 0.78 to 0.89 against each other regardless of behavior, while real
functions measured 24 or more and two genuinely different ones scored 0.64.

**The comprehension scorer was defeated by padding.** The first version measured function
word density alone. An answer consisting of a keyword list padded with the article "the"
scored 1.0 and passed. The measurement was replaced by a composite additionally requiring a
linking word and vocabulary of the answer's own.

**A regex was silently disabled by control characters.** An exception-matching pattern
contained literal `0x08` bytes introduced by escape mangling during editing, invisible in
the file, which disabled the check entirely. A repository-wide control character scan now
runs alongside the ASCII scan.

**Chain breaks did not propagate.** Link verification originally compared against the
predecessor's stored hash rather than its recomputed hash. Under it, an edited entry was
reported as tampered while every following entry reported as verified, defeating the
property a hash chain exists to provide. Found by the Phase 4 exit criterion requiring the
first point of failure to be named.

**Unavailable answers were scored as wrong answers.** `isatty` reported a usable terminal,
`input` then returned end-of-file immediately, and the resulting empty answers were scored
as failures that refused the commit. Answers that cannot be collected are not answers that
were wrong; the failed read is now the signal.

**The published fingerprint did not match the published report.** During documentation, an
example fingerprint from a scratch repository was published in the README while the
committed report was signed by the actual key. A reader following the repository's own
verification instructions would have received a mismatch on a legitimate artifact. Found by
executing the documented instructions rather than reading them.

### 6.3 Verification behavior

The three-chain criterion produces three distinct outcomes over identical content:

- An untouched chain: all entries `verified`, chain intact, exit 0.
- One mutated field: that entry `tampered`, every following entry `chain_broken`, the first
  point of failure named, exit 1.
- A legitimately re-signed chain from a different interpreter: that entry
  `unverifiable_version` with every cryptographic check passing, exit 0.

The three-report criterion likewise produces three outcomes, of which the third is the
significant one: a report generated from a ledger re-signed under a substitute key,
carrying a fabricated perfect comprehension record, **verifies internally**. It is caught
only by comparing the displayed fingerprint against an independently obtained copy.

## 7. Limitations

We state these without qualification. A provenance system that overstates itself is worse
than none, because it produces confident artifacts that do not support the conclusions
drawn from them.

### 7.1 Stylometry does not detect AI

The stylometric path measures whether code resembles the rest of a repository. It does not
detect machine generation, and no local statistic can. Confidence is always reported, is
capped below certainty, and the path declines outright below its minimum baseline and hunk
sizes. On the self-application it averaged 0.245, which is weak.

### 7.2 The comprehension scorer measures consistency, not understanding

It determines whether an answer is structurally consistent with the code. Someone who
reasons to the correct answer without reading the code defeats it. More seriously, someone
who reads the scoring logic could construct an answer satisfying the measurements without
comprehension. The first version of the scorer was defeated in a single attempt by its own
author; we regard the current version as harder to defeat, not as undefeatable, and we do
not claim a bound on the effort required.

### 7.3 A signature proves consistency, not identity

Anyone may generate a key, write a ledger, and sign a report. That report verifies. The
fingerprint comparison is the mechanism that establishes origin, and it functions only when
the verifier obtains the fingerprint by a route the report's author does not control. This
is mitigation dependent on verifier behavior, not a property of the artifact.

### 7.4 The gate acts on evidence, not inference

The continuous integration gate defaults to a confidence threshold of 0.9, which covers
tool signals and structural proof and excludes stylometry by construction. On a repository
with no assistant integration, the gate passes almost everything. This is deliberate:
failing a contributor's build on a heuristic's inference is the overreach this work argues
against. It also means the gate enforces accountability for code known to be
AI-generated and does not detect code nobody reported.

### 7.5 Retroactive scans are reconstruction

Scanned entries are marked distinctly, use stylometry alone, and carry no comprehension
outcome, because a developer cannot be meaningfully questioned months later about code
sitting in front of them. The baseline bias described in Section 6.1 applies.

### 7.6 Scope

Python only. No passphrase on the private key, on the grounds that the threat model already
excludes a compromised local machine and a per-commit prompt would make the tool
intolerable. No key rotation. The private key is written owner-read-write, which is a
documented no-op on Windows, where the file inherits directory permissions.

### 7.7 Evaluation limitations

No labelled ground-truth corpus was used, so no attribution accuracy figure is reported.
Self-application is a single case study on a repository written by the system's own author,
which is a weak basis for generalization. The 45.2 percent figure characterizes this
repository under this measurement, not AI-assisted development generally.

## 8. Discussion

The strongest result of this work is not the attribution percentage. It is the
demonstration in Section 6.3 that a forged report verifies. A system whose security
narrative depended on signatures alone would have shipped that as a success. Stating the
limit, and then showing the mechanism that addresses it, is a more defensible position than
claiming a limit does not exist.

The same reasoning governs the confidence model. A single blended confidence number would
be easier to display and would destroy the distinction between a proof, a report, and a
guess. Carrying three epistemic categories through to the report costs presentation
simplicity and buys a reader the ability to discount inference appropriately.

We regard the adversarial phase methodology as the most transferable contribution. Six of
the defects in Section 6.2 were found by a criterion fixed before implementation, and at
least one, the weak similarity signature, would have passed a conventionally written test
suite. Writing the hard case first, and then attempting to defeat one's own implementation,
surfaced failures that ordinary testing did not.

---

## 9. Conclusion

Vouchcode addresses a gap left open by the current generation of AI provenance tooling: the
absence of any mechanism verifying that the accountable human author of a commit
understands the AI-generated code they are committing. By combining local-first,
zero-dependency syntax tree analysis, a deterministic comprehension engine, and a
cryptographically tamper-evident ledger, it extends attribution into accountability while
remaining installable in a single command.

Self-application produced 62 verified ledger entries and an AI attribution of 45.2
percent at a mean confidence of 0.245, reported with the conservative bias of the measurement
stated rather than omitted. Six classes of defect were surfaced by an adversarial
development methodology and are reported alongside the results.

The system's limits are real and are stated in the artifacts it produces, not only in this
paper. A signature proves a document is unaltered, not who produced it. A comprehension
score measures structural consistency, not understanding. What the system provides is not
certainty but a set of claims a third party can check offline, which is a meaningful
improvement over a claim that can only be asserted.
